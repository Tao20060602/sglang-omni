## 它说了什么(原文要点,分三类)

### 一、它指出的错误,我认可并已改

1. **步长分解对不上**:2.30 + 4.09 + 0.11 = 6.5 ms,而我报的步长 p50 是 7.62 ms,
   有 1.1 ms 没有归属。原因是把各分量各自的 p50 相加当成了关键路径。
   → 第二十二轮的表已改成"各分量各自的 p50,不可相加",并标出未归属的 1.1 ms。
2. **分母串了**:我说小 GEMM 占 predictor 60%,那是 rps 1 的 1.98 ms / 3.34 ms;
   但我把它和 rps 20 的 4.09 ms 摆在一起,按后者算应是 48%。→ 已分开写。
3. **"提前半个迭代"是部分请求的收益,不是平均收益**:设迭代周期 T、到达均匀分布、
   两个收信点相隔 a,平均等待从 T/2 降到 (a² + (T-a)²)/(2T),最大降幅是 T/4。
   T = 7.6 ms 时最多把平均收信等待从 3.8 ms 降到 1.9 ms,不是我说的 3 ms。
4. **代码里的"中间"不等于时间上的中间**:`run_batch_launch` 是异步的,调用返回得很快,
   所以插在它后面的第二个收信点在**时间上**可能离第一个只有一两毫秒,迭代的大部分墙钟
   还在后面(等 GPU、resolve、发流)。要先量两个收信点的实际时间间隔。
   → 这是本次外审最有价值的一条,直接影响 C10 能不能work。

### 二、它反对、但我坚持的

- 它认为应优先做 GEMM 族(每帧 1.98 ms,是采样内核的 6.3 倍),而不是调度。
  我坚持先做调度:GEMM 的 1.98 ms 是 **rps 1** 的数字,那时每个 GEMM 只算一行、
  纯属开销;rps 20 下同族内核分片变大、效率已经接近合理,而 rps 20 才是我们要追的
  指标。它没有这个"低负载低效、高负载合理"的分解,所以高估了 GEMM 的可回收时间。
  这一点写进下一轮 run doc,若 C10 实测为零则回到 GEMM。

### 三、它同意但补强的(我采纳)

- 2x2 消融:#2216 的 2 ms 等待 开/关 x C10 开/关。否则两者可能都在消除"错过同一个
  批次截止"这一件事,收益会被重复计算。→ 加一个"关 2 ms 等待、开 C10"的臂。
- A/A 对照:同一 binary 跑两次给出协议本身的噪声,再拿它比 A/B 的差值。
  我们已有首尾各跑一次 main 的做法,这轮明确当作 A/A 用。
- 随机化配对顺序、同一 build 下用开关切换,而不是"上午跑 baseline、下午跑 patch"。
- 它列的中途收信危险边界里,对我们真正成立的两条:两个收信点可能把同一请求提交两次
  (由 `_pending_request_builds` 在锁内查重挡住);TP>1 时两个收信点都含 broadcast,
  各 rank 必须对称执行(当前 predictor 图路径本来就只支持 TP=1)。
  它担心的"改动已发射批次所属状态"不成立:`abort` 默认 `defer_running_cleanup=True`,
  在飞请求只标记不回收 KV。

## 我的原判断(发审前写下,原样保留)

下一步实现 C10:在调度循环一次迭代的中间(刚 launch 完 GPU、还没 resolve 上一步时)
再收一次信箱并提交 request build。理由是剖面显示 GPU 侧候选都只值百分之几的步长,
而准入链路上仍有两段各 6-8 ms 的等待,且同族的 C1 已实测 -8 ms。预期 -3 ms。
最不确定的地方:中途收信会不会让 build 线程池和主循环争 CPU;6.3 ms 这个数字来自被
事件记录器干扰过的一轮。

判断与外审的差:我预期 -3 ms,它算出上限 1.9 ms 且指出插入点可能根本不在时间中点。
实测以 A/B 为准。
